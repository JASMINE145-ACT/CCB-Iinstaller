# CCB-Wanding 项目 - 面试 STAR 回答

> **适用问题：** “你落地过哪些 AI 项目？”“完整讲一个 AI 项目的落地过程。”  
> **建议时长：** 主回答约 3 分钟；30 秒版本可单独使用。  
> **表达原则：** 先讲业务闭环和个人责任，再展开技术架构。

## 3 分钟 STAR 主回答

### S - Situation

我主导落地了一套面向 **B2B 贸易报价场景** 的企业桌面 Agent 产品 CCB-Wanding。

业务员日常需要在 Windows 上处理询价 Excel、匹配多档价格、查库存、填写报价单。价格规则和业务经验分散在表格、历史报价单和个人经验中，新员工上手慢，人工操作也容易出错。客户现场还有内网、本地文件和离线使用要求，纯 SaaS 方案并不适合。

项目最初已经有 AionUI、Agent 运行时和报价 MCP，但 UI、ACP 桥接、运行时、Python 业务能力分布在不同层和不同运行目录。最典型的问题是：代码改了、构建也通过了，但员工安装后的实际行为没有变化。

所以真正的挑战不是做一个聊天界面，而是把分散的 AI 能力变成一个 **可安装、可鉴权、可升级、可回归** 的生产系统。

### T - Task

我的核心职责是端到端打通这条产品链，重点负责四件事：

1. 划清 UI、ACP、MCP 和业务服务的责任边界，解决跨层问题反复打补丁的情况。
2. 把询价、填表、查库存和知识沉淀设计成可控的 Agent 工作流。
3. 建立组织登录、价格库、知识库及写操作的权限和一致性机制。
4. 建立从源码构建到员工安装环境的交付和验收体系。

我的目标不是让模型“看起来会做”，而是让员工能够每天稳定使用，并且出了问题可以定位、回归和审计。

### A - Action

#### 1. 先治理架构边界

我先把系统明确拆成四层：

```text
AionUI 桌面端
    -> ACP / route-b 桥接
    -> Agent 运行时与 MCP 注册
    -> Python 报价、价格库和组织知识服务
```

我把一条规则写进项目 spec：**ACP、MCP 和会话问题优先修生产者源码，不在前端堆补丁。**

这解决了一个长期问题：过去团队容易在 UI 层修表象，真实错误仍留在运行时。分层之后，每类故障都有明确的责任模块、构建路径和验证方法。

#### 2. 用确定性工程约束模型

我没有把业务正确性寄托在一个大 prompt 上，而是采用 **Agent + Skill + MCP** 的分工：

- Agent 负责理解用户意图和选择工作流。
- Skill 固化可复用 SOP，例如报价、填表和按数据学习。
- MCP 与 Python 负责价格匹配、文件修改、权限检查和组织数据写入。

在智能报价场景中，用户可以上传 Excel 或截图，Agent 调用结构化工具完成匹配和填表；出现多个候选时先澄清，不让模型自行猜测。

对于有副作用的操作，我统一采用：

```text
读取当前状态 -> 展示预览 -> 用户确认 -> 执行写入 -> 重新读取验收
```

例如 Agent 学到新业务规则后，不能直接修改本地文件，而是先展示待写内容，得到确认后再写入组织知识库。模型负责理解，确定性代码负责守住数据边界。

#### 3. 解决桌面端身份与跨进程一致性

这类产品最复杂的问题往往不在模型，而在桌面端的身份和运行环境。

一个典型问题是：AionUI 页面已经登录，组织数据也能读取，但 Agent 写组织知识持续返回 401。最终我定位到 Dev 和 Prod 使用不同 AppData 目录，MCP 子进程读取了过期的 Prod JWT。

我没有用无限重试掩盖问题，而是抽象统一的 `org_session`：

- 显式绑定当前 AppData profile。
- 统一桌面端和 MCP 子进程的 token 来源。
- 区分 401、403 和 409，分别处理身份过期、权限/CSRF 和版本冲突。

同时，卡片隐藏只作为体验控制；真正的安全边界仍在服务端 RBAC、CSRF 和版本校验。即使模型误调用写工具，非管理员也不能修改组织数据。

#### 4. 把个人工具升级为组织资产

我推动价格和业务知识从本地文件迁移到组织 API：

- 组织价格库成为统一权威源，当前覆盖 **42 个字段、3299 条商品**。
- 报价 Agent 从同一远端版本读取价格，避免员工各自维护不同 Excel。
- 新规则经过确认后写回组织知识库，而不是只留在某台电脑。
- 统一 SSO 让桌面端、MCP 和组织写库使用同一身份链路。

这一步把“个人效率工具”升级成了可共享、可管理的组织能力。

#### 5. 建立真实交付链

桌面 AI 最容易停在“我的机器上能跑”。因此我建立了完整交付链：

```text
源码修改
  -> 构建
  -> vendor / 配置同步
  -> MCP 健康检查
  -> Windows 安装包或热更新
  -> 员工环境 smoke
```

验收标准不再是“代码编译通过”，而是新安装环境能否完成一次真实闭环，例如：

```text
上传询价表 -> 匹配价格 -> 填写报价单 -> 输出结果
```

项目过程通过 Trellis 固化为 PRD、实现、review、测试和 spec 回写，使关键经验可以被后续开发复用。

### R - Result

最终，这套系统从多层拼装的 Agent demo 演进成了可交付的 Windows 桌面产品：

- 员工可以从 Guid 直接进入报价、账务、Excel 等领域 Agent。
- 询价、查库存、填表和知识沉淀形成了可复用业务闭环。
- 价格库和知识库进入组织统一治理，写操作具备身份、权限、CSRF 和版本冲突保护。
- 四层架构有了清晰边界，Agent、Skill 和 MCP 契约进入 spec。
- MCP health、单元测试、真实账号 E2E 和安装环境 smoke 共同覆盖交付链。

这个项目让我形成了一个很明确的判断：

> 企业 AI 落地不是单纯提升模型效果，而是把模型的不确定性纳入权限、数据、测试和交付体系。

## 30 秒版本

> 我主导落地了一套面向 B2B 报价场景的企业桌面 Agent 产品。项目最初已经有 UI、Agent 运行时和报价工具，但各层分散，开发环境能跑不代表员工安装后可用。我负责打通 AionUI、ACP、MCP 和 Python 业务四层，通过 Agent、Skill 和结构化工具完成询价、填表、查库存与组织知识沉淀；同时补齐 SSO、RBAC、CSRF、版本冲突、健康检查和 Windows 交付链。核心成果是把一个 Agent demo 变成了可安装、可升级、可审计、可回归的生产工具。

## 最能体现个人价值的案例

### 案例一：为什么 UI 登录成功，Agent 写库仍然 401？

**问题：** AionUI 可以读取组织数据，但 MCP 写组织知识失败。  
**定位：** Dev/Prod 双 AppData 环境导致 MCP 子进程读取过期 JWT。  
**解决：** 抽象 `org_session`，显式绑定 profile，统一 token 来源并分类处理 HTTP 错误。  
**价值：** 体现跨进程、认证、桌面运行环境和根因治理能力。

### 案例二：为什么构建成功，员工机器仍然没有新功能？

**问题：** 源码、vendor、安装目录、用户配置和运行时不是同一层。  
**解决：** 建立源码到员工环境的四层验证链，并增加 MCP health 与 smoke。  
**价值：** 体现工程交付和生产 ownership，而不只是功能开发。

### 案例三：如何避免 Agent 误写组织数据？

**问题：** 模型可能误解用户意图或跳过确认。  
**解决：** 预览、确认、执行、验收协议；服务端 RBAC + CSRF + revision 作为最终安全边界。  
**价值：** 体现 Agent 工程、安全设计和人机协同能力。

## 追问速答

| 面试官追问 | 回答重点 |
|------------|----------|
| **你个人贡献最大的部分是什么？** | 四层边界治理、Agent 确定性约束、组织身份链和真实交付闭环 |
| **你和团队如何分工？** | 说明你主导的设计、实现和验收范围；明确其他成员负责的模块，不把团队成果全部归于个人 |
| **你和 LLM 如何分工？** | LLM 理解意图、生成候选；MCP/Python 负责数据、权限、文件和副作用 |
| **如何减少幻觉？** | 结构化工具、权威数据源、候选澄清、写前预览、执行后重新读取 |
| **如何保证写操作安全？** | UI 隐藏不是安全边界；服务端 RBAC、CSRF、revision 和审计共同约束 |
| **最大技术难点是什么？** | 多仓、多进程、多运行目录导致行为不一致；通过分层和端到端验证解决 |
| **为什么做桌面而不是 Web？** | Windows 本地文件、内网/离线、长期会话、受控安装与更新 |
| **如何评估效果？** | 业务闭环完成率、工具成功率、人工接管率、错误分类、E2E 和安装环境 smoke |
| **如果重做一次会改什么？** | 更早建立统一身份模块、运行目录清单和端到端基线测试 |

## 按岗位调整主叙事

| 岗位方向 | 优先强调 |

## 面试前补充的量化数据

以下数字只有在可以核实时再加入主回答：

- 实际安装或试用人数。
- 单次报价平均耗时前后对比。
- 报价匹配准确率或人工修正率。
- MCP 工具调用成功率。
- 发布频率和部署耗时。
- 自动化测试、健康检查和 E2E 场景数量。

不要用“显著提升”“大幅降低”替代证据。没有业务统计时，可以使用 **42 个价格字段、3299 条商品、测试通过数、健康检查项数** 等工程验收数据。
