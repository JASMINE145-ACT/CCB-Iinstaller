  质疑 1:许可证风险(最致命)

  文档说"fork AionUI 前端",但 AionUI 是 iFlow 的项目,大概率不是 MIT/Apache 这种允许改名商用 + 闭源 fork 的协议。

  必须先做的事:https://github.com/iFlow-OSS/AionUI 的 LICENSE 翻一遍,看清楚:
  - 是否允许商用
  - 是否允许修改后改名
  - 是否需要保留版权声明
  - 静态资源(字体、图标)的来源(Lucide / 自有 / 第三方?)

  如果是不友好的协议,Path C 在法律层面就走不通,后面所有的工作量都是沉没成本。

  ---
  质疑 2:"只改三类东西"是过度乐观

  文档原话:
  1. Logo / 名称 / 品牌
  2. 后端 API 地址
  3. 消息和工具调用的数据适配

  第 3 项实际上是改 AionUI 前端的核心数据流层。AionUI 的 React 组件、状态管理(Zustand/Redux)、事件订阅、WebSocket        
  reconnection、断线重传——这些都和后端协议耦合。

  工程现实是:你把 localhost:5000 改成 localhost:7933 一行的事,但要让 AionUI 的"消息组件"认你的事件格式,你可能要重写 30%  
  的前端源码。

  工作量不一定比"仿写一个简化版 UI"小,只是换了个坑。

  ---
  质疑 3:AionUI 的部署形态假设不明

  文档通篇说"前端以为自己还在和 AionUI 后端说话",但没明确 AionUI 是:
  - Electron 桌面应用?如果是这样,前后端走 IPC,根本不是 HTTP/WebSocket 协议,你的 serve-wanding.js 没法插入
  - Web 应用?如果是这样,要看它有没有 SSR、cookie session、CORS 等
  - 混合(本地 HTTP + Web UI)?这才是最可能的情况,但要搞清楚本地后端暴露的端口和协议

  第一步应该是确认 AionUI 的部署形态,然后才能决定 Path C 的可行性。

  ---
  质疑 4:工具调用卡片是最大坑,被一笔带过

  文档举的例子:
  tool_call: inventory_search
  → AionUI 显示:正在调用工具:库存查询

  但 AionUI 真实的工具卡片支持:文件预览、表格、图表、代码 diff、图像、PDF 渲染、JSON 折叠树——每种内容都有专门的 React    
  组件。

  要让 CCB-Wanding 的工具结果也呈现这种视觉,你必须在 serve-wanding.js 里自己渲染或传输这套 rich
  content。本质上就是从零做一个 mini AionUI tool renderer。

  这是方案里工作量最大、最容易被低估的部分,文档完全没展开。

  ---
  质疑 5:升级维护陷阱

  一旦 fork 了 AionUI 前端,你就面临:
  - AionUI 自己也在迭代,你的 fork 会越来越落后
  - 要么投入人力持续 merge upstream(每次 AionUI 发版你都要评估冲突)
  - 要么冻结版本,吃技术债到天荒地老

  这和直接用 AionUI 的坑是同一类坑,只是换了个地方。

  ---
  质疑 6:功能空缺问题

  AionUI 有一堆 CCB-Wanding 未必对等的功能:
  - 多模型切换(MiniMax/Claude/GPT 同时挂着)
  - 会话分支 / 重新生成 / 消息编辑
  - 文件上传下载
  - 设置页(主题、快捷键、API Key)
  - 历史会话搜索
  - 计划模式 / 权限模式

  每缺一个,前端就会出现点不动的按钮 / 空状态 / 半成品界面,这比"土"更难看。

  ---

  ---
  我会怎么建议推进顺序

  如果你坚持走 Path C,建议这样降风险:

  1. 先看许可证(1 小时定生死)
  2. 把 AionUI 前端单独跑起来,DevTools 看它到底调了哪些接口(2 小时)
  3. 写一个 mock 后端,返回硬编码数据,验证 AionUI 前端能不能"假装"和你的后端对话(半天)
  4. 评估真实接口数量:如果 < 20 个,Path C 可行;如果 > 50 个,改走 Path D
  5. 再做 CCB-Wanding agent loop 的接入

  第 3 步是分水岭——如果 mock 后端能让 AionUI 前端跑通 80% 界面,Path C 就是真的;如果连 mock 都要做 50 个接口,说明 AionUI  
  前端和它的后端耦合度太高,Path C 的工作量就不划算了。
