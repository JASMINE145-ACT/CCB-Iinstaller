# 2026-05-27 CCB 安装包终端界面异常修复记录

## 问题描述

安装 `ccb-installer\CCB-Setup-1.0.1.exe` 后启动 CCB，在 Windows 终端中出现以下问题：

- 启动顶部输出“系统找不到指定的驱动器。”
- 欢迎界面边框断裂，出现多余的 `|` 字符。
- 中文输入和回复发生重叠、重复渲染。
- 状态提示、快捷键提示、输入区域位置错乱。
- 界面难以正常阅读和操作。

使用环境：

- 工具：Claude Code CLI / CCB
- CLI 版本：`2.1.888 (Claude Code)`
- 模型配置：`minimax-m2.7`
- 系统：Windows 10/11

## 定位结论

该问题主要来自 Windows 启动与终端渲染兼容性，不是 MiniMax 模型响应内容导致的。

### 1. 驱动器错误来源

原 `ccb.cmd` 会优先探测系统 Git Bash。当前环境的系统 Git 位于 `D:\Git\cmd\git.exe`，入口脚本启动链会在系统 Git 探测阶段产生：

```text
The system cannot find the drive specified.
```

隔离验证结果：

- 直接执行打包的 `cli.js --version`：无错误。
- 设置配置目录或关闭 fullscreen 后直接执行：无错误。
- 通过原 `ccb.cmd --version` 执行：可以复现驱动器错误。
- 隐藏系统 Git 探测并使用安装包内置 Git Bash：错误消失。

安装包已经自带 Git Bash，因此启动时探测用户机器上的外部 Git 没有必要，且会引入盘符与安装路径风险。

### 2. TUI 重叠绘制来源

在打包 CLI 代码中确认存在 fullscreen/备用屏幕渲染逻辑，并支持环境变量：

```text
CLAUDE_CODE_NO_FLICKER=0
```

该值会关闭 fullscreen 渲染。在部分 Windows 控制台宿主中，备用屏幕、光标移动和屏幕差量刷新支持不完整，可能导致边框错位、中文重叠和重复绘制。

原入口脚本还会设置：

```bat
set "TERM=xterm-256color"
```

这会把普通 Windows 控制台标记成具备较完整 ANSI 能力的终端，增加错误渲染风险。

### 3. 快捷方式绕过入口脚本

原安装器生成的桌面和开始菜单快捷方式直接执行：

```text
bun.exe dist\cli.js
```

这会绕过 `ccb.cmd`，导致配置目录、Git Bash 路径以及兼容环境变量没有统一生效。

### 4. 配置模板存在密钥泄漏

安装器内的 `resources\settings\settings.json` 曾包含明文 `ANTHROPIC_API_KEY`。这意味着旧安装包中已经打包了可提取的 API Key，必须撤销并轮换该密钥。

### 5. NSIS 脚本编码损坏

重建安装包时发现原 `installer.nsi` 存在乱码/混合编码，NSIS 编译报错：

```text
Bad text encoding: ...\installer.nsi:57
```

因此将安装脚本文案规范为 ASCII 兼容文本，并继续保留简体中文向导语言。

## 终端渲染后续决策

- VS Code 集成终端通常不易复现叠字，是因为其终端实现对 ANSI 光标移动、备用屏幕与 Unicode 字符宽度支持更完整；双击 `.cmd` 启动的传统 Windows 控制台兼容性较弱。
- 当前采取的优先方案是修复启动宿主：桌面入口优先进入 Windows Terminal，同时在旧终端回退路径降低 TUI 渲染能力要求。
- 暂不开发独立 UI。为 Claude Code CLI 包一层聊天 UI 不只是显示输入输出，还需要处理工具调用、权限确认、流式消息、会话恢复、中断和错误呈现，开发与维护成本高于终端兼容修复。
- 若重新安装并在 Windows Terminal 中仍可稳定复现界面叠字，再评估第二阶段 UI 外壳，且应基于非交互/结构化流协议而不是嵌套显示原 TUI。

## Windows Terminal 复测仍失败及缩放崩溃

用户复测确认：

- 即便按上述方案使用更可靠的终端宿主，界面混乱仍存在。
- 对终端窗口执行放大或缩小时，程序会直接退出，窗口消失。

进一步检查打包 CLI (`2.1.888`) 后确认：

- 交互渲染器会注册 `stdout.on("resize", this.handleResize)`。
- 窗口宽度或高度变化会进入 `fullResetSequence_CAUSES_FLICKER(..., "resize")` 的整屏重绘路径。
- `CLAUDE_CODE_NO_FLICKER=0` 只能关闭 fullscreen 模式，不能关闭普通渲染器的 resize 监听。
- `CLAUDE_CODE_ACCESSIBILITY` 在该打包版本中仅能确认会影响光标显示行为，不能证明可规避 resize 重绘崩溃。

因此，该阶段不能将问题继续归因于 CMD 或 Windows Terminal 单独的能力差异，也不能宣称仅依赖环境变量已经修复。故障已进入 CLI 内部交互渲染/窗口 resize 路径，需要实际退出日志后才能安全修改。

## 终端内 resize 兼容补丁

用户进一步明确不开发新的 UI，继续使用终端。因此对已确认的渲染器故障路径作最小范围处理：

- 在 `ccb.cmd` 与 `ccb-template.cmd` 中默认设置 `CLAUDE_CODE_DISABLE_TUI_RESIZE=1`。
- 在打包渲染器 `dist\chunk-z9bw4q7j.js` 中读取上述开关；启用时不注册 `stdout` 的 `resize` 回调。
- 保留现有终端交互、UTF-8 和非 fullscreen 兼容模式，不改变模型/API 通道。

处理依据：

- 原渲染器在窗口尺寸改变时会调用 `handleResize`。
- 宽度变化随后进入 `fullResetSequence_CAUSES_FLICKER(..., "resize")`，执行清屏并整帧重绘。
- 用户报告的缩放后叠字与程序消失，正好发生在该路径被触发时。

行为限制：

- CCB 会按启动时的终端宽高完成布局；运行中缩放窗口不再触发 CLI 内部实时重排。
- 如需改变窗口大小，应先退出 CCB，调整终端尺寸后重新启动。
- 需要恢复原始实时缩放行为时，可在启动前设置 `CCB_ENABLE_TUI_RESIZE=1`；该模式仍可能复现当前故障。

该补丁专门规避 Windows 终端中的 resize 整屏重绘路径，不声称修复 Claude Code 上游渲染器的所有中文宽度问题。若在完全不缩放窗口的条件下仍出现初始界面叠字，应使用 `CCB Diagnostics` 保留日志继续定位。

## 初始布局错位继续处理

用户在不以缩放崩溃为主要触发条件的截图中仍观察到边框断裂和错位，说明 resize 补丁仅覆盖了一条故障路径，不能解决初始布局问题。

进一步检查打包渲染器确认：

- `isEastAsianWide()` 已将常用中文代码区段按双列处理，因此目前没有证据支持直接修改中文宽度算法。
- `CLAUDE_CODE_NO_FLICKER=0` 会关闭 fullscreen；在该模式下主界面仍使用普通屏幕上的增量绘制/滚动区处理。
- Windows Terminal 与 VS Code/Cursor 均支持备用屏绘制，适合优先避开普通屏幕旧内容残留路径。

因此调整 `ccb.cmd` 与 `ccb-template.cmd` 的默认策略：

- Windows Terminal（存在 `WT_SESSION`）或 VS Code/Cursor 集成终端（`TERM_PROGRAM=vscode`）：默认设置 `CLAUDE_CODE_NO_FLICKER=1`，启用 fullscreen 备用屏。
- 传统控制台回退路径：继续设置 `CLAUDE_CODE_NO_FLICKER=0`。
- 所有默认路径仍设置 `CLAUDE_CODE_DISABLE_VIRTUAL_SCROLL=1`、`CLAUDE_CODE_DISABLE_MOUSE=1` 与 `CLAUDE_CODE_DISABLE_TUI_RESIZE=1`，避免引入已知 resize 崩溃路径。

对比开关：

```powershell

& "$env:LOCALAPPDATA\Programs\CCB\ccb.cmd"
```

该开关用于确认 fullscreen 与非 fullscreen 对初始错位的影响，不应作为默认日常用法。
